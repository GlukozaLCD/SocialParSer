# Проектный план — мультиплатформенный сборщик данных соцсетей

Среда: Instagram, TikTok, VK, Telegram, YouTube.

## Идейные столпы

1. **Охват платформ.** Instagram, TikTok, VK, Telegram, YouTube — все пять должны поддерживаться одним и тем же пайплайном (общая схема данных, разные адаптеры под капотом).

2. **Приоритетная задача №1 — ежедневный сбор ссылок.** Каждый день собирать ссылки на посты, вышедшие за последние 24 часа, и сортировать их по пабликам из отслеживаемого списка (список пабликов задаётся заранее и подлежит загрузке/редактированию).

3. **Приоритетная задача №2 — метрики постов.** По списку постов (полученному из задачи №1 или заданному отдельно) собирать: просмотры, лайки, комментарии, репосты, сохранения. Плюс отдельно — число подписчиков у самих групп/каналов/страниц из списка.

4. **Роль в конвейере.** Это не самостоятельный конечный продукт, а узел в цепочке ботов: собранные данные передаются по сети другому боту, который делает с ними что-то дальше. Значит, важен не только сбор, но и надёжная сдача результата наружу (см. допущения ниже).

5. **Доступ к платформам — смешанный подход:**
   - **VK, Telegram, YouTube** — через официальные API (стабильно, легально, без риска банов).
   - **Instagram, TikTok** — официальный API есть только для собственных Business/Creator аккаунтов. Для чужих публичных страниц из списка — неофициальный скрапинг с щадящими лимитами запросов, принимая риск блокировок/поломки при смене вёрстки платформы.

6. **Гибкость запуска.** Целевая среда исполнения (локальный ПК vs сервер) заранее неизвестна. Бот обязан поддерживать и ручной запуск (CLI), и автоматический (по расписанию), поэтому нельзя жёстко привязываться к одному способу планирования — нужно несколько вариантов на выбор.

7. **Стек.** Python.

8. **Портативность.** Всю папку проекта можно скопировать/переслать на другую машину — и там всё продолжает работать без ручной подгонки. Никаких абсолютных путей и никаких системных/пользовательских директорий ОС (APPDATA, `~/.config` и т.п.) для конфигов, сессий, логов и результатов — всё живёт внутри самой папки проекта, только относительными путями от её корня.

9. **Понятность для стороннего пользователя.** Программу должен суметь поставить и использовать человек, который её не писал. Это значит: важные места в коде — с комментариями (что происходит и, если не очевидно, почему — а не пересказ кода строчка в строчку); `README.md` в корне проекта объясняет установку, настройку и запуск так, чтобы не нужно было лезть в исходники. README поддерживается в актуальном состоянии по ходу разработки, а не пишется один раз в конце.

## Открытые решения / допущения

- **Выдача результата:** пока принимающий бот неизвестен — ограничиваемся локальным файлом (JSON), который можно открыть и посмотреть напрямую. Никакой сетевой доставки (вебхуков, очередей и т.п.) на этом этапе не строим. Когда появится ясность по интерфейсу принимающего бота — переделывается один изолированный шаг (запись результата), а не весь пайплайн.
- **Список пабликов и учётные данные платформ:** задаются и редактируются пользователем через встроенное меню самой программы — мастер первого запуска и меню настроек, доступное в любой момент (добавить/изменить/убрать паблик или токен). Ручное редактирование конфиг-файлов не требуется от пользователя; внутри данные всё равно хранятся как структурированный файл (JSON), но точка входа для пользователя — меню, а не текстовый редактор.
- **Портативность Python-окружения:** сам venv копированием папки не переносится (внутри него — абсолютные пути и платформозависимые бинарники). Переносимость окружения обеспечивается bootstrap-скриптом, который на новой машине заново создаёт venv и ставит зависимости из `requirements.txt`, а не копированием готового venv.
- **Приватность и git:** репозиторий пока не инициализирован. Когда будет `git init`, файлы в `.plans/` (черновики активных функциональных планов) и любые файлы с токенами/сессиями (учётные данные из меню настроек, cookies для IG/TikTok, сессии Telethon) должны уйти в `.gitignore` — секреты никогда не коммитятся.

### Ежедневный сбор ссылок на посты по пабликам — готово

Реализовано целиком, все 4 фазы. Мастер первого запуска и меню настроек (`src/menu/`) поверх хранилища конфигурации (`src/config_store.py`) → адаптеры всех пяти платформ, включая интерфейс и фабрику (`src/adapters/`) → оркестровка сбора, группировка по пабликам и запись результата (`src/collector.py`, `src/output_writer.py`) → ручной запуск, встроенный планировщик и инструкция по Task Scheduler/cron (`src/scheduler.py`, README «Автоматический запуск по расписанию»). Актуальное поведение программы — в README.md; временный файл функционального плана (`.plans/PLAN_daily-links.md`) удалён по завершении, как и предполагает эта иерархия планирования.

### Сбор метрик постов и подписчиков — готово

Реализовано целиком, все 4 фазы. Расширил общую схему поста полем `post_id` (нужно было для повторного поиска поста через API — особенно для Instagram graph_api, где сохранённая ссылка не годится напрямую). Добавил во все адаптеры `fetch_post_metrics`/`fetch_subscriber_count` (`src/adapters/`) — с честной таблицей того, что каждая платформа реально отдаёт (не все пять метрик доступны везде — где нет, там `null`, не выдуманный ноль). Оркестровка — `src/metrics_collector.py`; по умолчанию встроена прямо в `python main.py run-once` (и в `run-daemon`) — ссылки и метрики собираются одним проходом без лишнего чтения файлов с диска, с флагами `--skip-metrics`/`--skip-subscribers` для отключения части работы; отдельная команда `collect-metrics` — для пересчёта метрик по уже собранным ссылкам. Актуальная схема результата (`data/output/metrics_<дата>.json`) — в README.md; временный файл плана (`.plans/PLAN_post-metrics.md`) удалён по завершении.
